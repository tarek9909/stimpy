# Decisions log

Append-only. Format: `- [area] decision, reason`. Specs: `docs/website/` (open-questions.md and api-reference.md win over older text).

## Backend foundation (B0-B2)

- [errors] Added error code `METHOD_NOT_ALLOWED` (HTTP 405, `details.allowed`, `Allow` header). The brief asks for 404/405 handling and the table in api-reference section 1 has no 405 code; the frontends only switch on the documented codes and fall back to the HTTP status.
- [errors] A JSON body over 100 KB is `413 FILE_TOO_LARGE` with `details.maxBytes`, malformed JSON / wrong content type are `400 VALIDATION_ERROR` (`fields.body`). Reason: no dedicated code exists; FILE_TOO_LARGE is the only 413 in the table.
- [errors] `error.requestId` is on every error body, not only INTERNAL. `fields` exists only for VALIDATION_ERROR; `details` is always present (`null` when unused).
- [errors] Prisma P2002 / P2025 / P2003 that escape a service are mapped to 409 CONFLICT / 404 NOT_FOUND / 409 CONFLICT by the error handler as a safety net. Services should still check explicitly and give a field-specific message.
- [validation] Request objects are `z.strictObject` (unknown fields rejected). Zod issue messages that are Zod's defaults are rewritten to plain English ("This field is required.", "Must be at least 2 characters.", "Enter a valid email address."); messages written in a schema pass through unchanged.
- [validation] Unknown-field errors are reported per key (`customer.role: "Unknown field."`).
- [http] An empty request body with `Content-Type: application/json` is accepted as "no body" (clients commonly send that header on body-less POSTs such as logout). A route that requires a body then reports `fields.body`.
- [rate-limit] `@fastify/rate-limit` is NOT used. A small in-memory fixed-window limiter (`src/lib/rate-limiter.ts`) is used instead, because it must (a) use the injectable clock, (b) key by body values (phone, e-mail) and (c) throw the standard `AppError`. Rules are centralised in `RATE_RULES`. Public GETs are limited globally (300/min/IP); POST limits are applied per route.
- [rate-limit] Login counts every attempt (not only failures) per IP and per e-mail (5 / 15 min); a successful login resets only the e-mail counter. `Retry-After` is the seconds until the window ends.
- [cors] CORS is implemented by hand in `plugins/cors.ts` (the three route groups differ). Disallowed origins get no CORS headers (not a 403) so tools keep working; preflights from disallowed origins answer 204 without CORS headers. Public routes accept WEB_URL and ADMIN_URL origins (ADMIN for the live Builder preview), never credentials.
- [csrf] The Origin check (`plugins/origin-check.ts`) runs before authentication, so a wrong Origin on an unauthenticated POST is 403, not 401.
- [headers] `@fastify/helmet` is not installed; `plugins/security-headers.ts` sets the equivalent headers (nosniff, no-referrer, X-Frame-Options DENY, CSP `default-src 'none'; frame-ancestors 'none'`, CORP, HSTS only when COOKIE_SECURE=true). `/docs` (Swagger UI) is exempt from the CSP, `/uploads/*` gets a sandboxing CSP, `CORP: cross-origin` and `Content-Disposition: inline`.
- [cache] `/admin`, `/auth` and every non-GET response is `Cache-Control: no-store`; public GET routes opt in with `publicCache(reply, seconds)` (30 s default, 10 s for drops).
- [auth] Session cookie `stimpy_session`: HttpOnly, SameSite=Lax, Path=/, `Secure` per COOKIE_SECURE, `Max-Age` fixed at 30 days (the server alone enforces the sliding 7-day / absolute 30-day expiry; every authenticated request extends `expires_at` in the database).
- [auth] Argon2id cost: 19 MiB, 2 passes, 1 lane (OWASP minimum). Unknown e-mails are verified against a lazily built dummy hash for equal timing.
- [auth] Change password also rejects a new password equal to the current one (`fields.newPassword`) and has its own limiter (5 / 15 min per user). A 12+ character check exists in both the Zod body schema and the service.
- [auth] `requireAdmin` is an `onRequest` hook (not preHandler) so 401 always precedes body-validation errors. All `/admin/*` routes get it from the admin scope in `app.ts`; `/auth/me` and `/auth/change-password` use it per route.
- [auth] Common-password list is a short built-in set (about 50 entries >= 12 characters), compared case-insensitively.
- [config] Extra optional env variables beyond backend README section 6: `LOG_LEVEL`, `TRUST_PROXY`, `DISABLE_JOBS`, `MAILPIT_URL`, `TEST_DATABASE_URL`. `ADMIN_EMAIL` / `ADMIN_PASSWORD` are optional for the server (only the seed and `admin:create` need them). Production requires secure cookies, HTTPS non-placeholder public URLs without embedded credentials, a non-local/non-test database without sample credentials, and a real SMTP host; it also refuses the example admin password case-insensitively.
- [config] Relative `UPLOAD_DIR` is resolved against `backend`, not the current directory.
- [db] All primary and foreign keys are `INT UNSIGNED`. Extra `created_at` / `updated_at` columns exist on most tables beyond the minimum in data-model.md (harmless, consistent with "every table has created_at"). `order_items.created_at` and `order_stock_lines.created_at` were added for the same reason.
- [db] MySQL refuses CHECK constraints that mention columns used by foreign keys, so the planned "exactly one of variant_id / stimpie_id" check on `order_stock_lines` / `stock_movements` is enforced in the stock service instead. Real CHECKs exist for `hoodie_variants` / `stimpies` (`quantity >= 0`, `0 <= reserved <= quantity`), `packs.stimpie_count BETWEEN 1 AND 5` and `order_stock_lines.qty > 0`.
- [db] JSON columns have no defaults (MySQL/Prisma limitation); services always write `[]` / `{}` explicitly.
- [db] `counters.order_number.value` is the LAST ISSUED number (seed: `firstNumber - 1`). The first order gets `value + 1`. Raising `settings.orders.firstNumber` sets the counter to `firstNumber - 1`; a change to a value `<= value` is rejected on `orders.firstNumber`; re-sending the unchanged value is fine.
- [db] `drops.name` and `stimpies.name` are not unique (only slugs are).
- [settings] `GET /admin/settings` returns the four groups of api section 5.12; `delivery` and `setup` are stored in the same table and exposed through their own endpoints (`/admin/settings/delivery`, `/admin/setup/:key/done`) by work package B. The settings service reads and merges uncached on write, and clears its 5-second cache on every write in this process.
- [settings] Empty strings are NOT turned into null; nullable fields must be sent as `null`.
- [options] `/admin/colors` and `/admin/sizes` lists are `Page<...>` (default pageSize 25, max 100) as section 5 says for all lists, and include a read-only `available` sum over active hoodie variants.
- [options] Colours and sizes are shared definitions. Each hoodie selects its own colours and sizes; only selected colour x size pairs are purchasable and stocked. Adding or re-activating a shared option does not change any hoodie's selections. Hiding an option keeps its existing hoodie variants but hides them from storefront stock; selecting an already-used hidden option reactivates its variant rows.
- [options] Deleting a colour or size is refused with 409 CONFLICT ("Used by past orders. Hide it instead.") when any order stock line references one of its variants; otherwise its variants, their stock movements (and for sizes the chart values) are deleted with it.
- [options] Reorder (`PUT .../order`) requires exactly the full set of existing ids (no duplicates, none unknown, none missing) else `VALIDATION_ERROR` on `ids`; positions become 1..n.
- [options] Public `GET /size-chart` fills empty cells with `"-"` and lists active sizes only; `GET /admin/size-chart` lists every size and uses `""` for empty cells. Saving ignores empty values.
- [size-chart] `PUT /admin/size-chart` row `values` keys: an existing column id; `new:<index of the column in the columns array>` for a column sent without an id; or the client's temporary numeric id when that id is given on a column but does not exist yet (the server creates the column and maps the key). Columns not sent are deleted with their values; at least 1 and at most 12 columns; values max 30 chars (column limit); column labels unique case-insensitively (`columns.N.label`). The how-to-measure text is stored as `content_blocks.size_chart_howto = { "text": string }`.

Colours are Black, Cream, Stone, Coral (brief) rather than Black, Cream, Coral (data model).

- [email/queue] Claiming a row is a conditional `UPDATE ... WHERE id AND status='PENDING' AND next_attempt_at = <value read>` that pushes `next_attempt_at` 2 minutes ahead (a lease), because the schema has no in-flight status. A worker that dies mid-send therefore re-sends after the lease (at-least-once). Backoff after failed attempt 1/2/3 is +1/+5/+30 minutes from the failure time; the 4th failure sets FAILED. A successful send also counts the attempt (`attempts` = number of tries).

Manual resend (`resend: true`) bypasses both the idempotency check and the switches (the founder asked explicitly) but still needs a `contact_email`.

The blue button "Track your order" appears when the template body uses `{tracking_url}`. - [comms] Saving a template rejects every `{...}` token that is not an allowed placeholder (also `{Foo}`, `{}`, `{a-b}`), because only exact lower-case names are substituted and anything else would be left in an outgoing message. Preview is lenient (unknown placeholders render empty, no error) so typing does not flash errors; the server is strict on save. Test send returns `202 { id }` of the queued log row and uses the SAVED template. Email-log `at` is the time the row was queued (`created_at`). Retry returns `202 { id, status: 'PENDING' }`, resets attempts to 0, and answers 409 for a row that is not FAILED. `PUT /admin/whatsapp-templates` accepts the array as returned by GET (extra `name`/`placeholders` are ignored), may contain a subset, and rejects unknown keys and duplicates.
- [customers] `ordersCount` = non-cancelled orders (same rule as "repeat customer"), `totalSpentCents` = sum of `total_cents` of DELIVERED orders, `lastOrderAt` = latest `placed_at` of a non-cancelled order (null if none). Additive fields `returnedCount` and `warning` (3 or more RETURNED orders, business-rules 13) are returned in the list and detail so the dashboard can show the warning badge. Customer notes are limited to 2000 characters (dashboard-pages 10.2).
- [search] LIKE wildcards typed by the user (`%`, `_`) are escaped (`lib/like.ts`): Prisma's `contains` does not escape them. WP-B's order search should use `likeEscape` too.
- [finance] `GET /admin/finance/profit` adds a `note` string ("Based on current order statuses...") and `byOrder[].date` is the delivery date as `YYYY-MM-DD` in the business timezone, newest first. `from`/`to` are inclusive date-only strings in the business timezone; a missing bound is open (all time). The cash view (`/admin/finance/cash`) lists every unsettled DELIVERED order plus DELIVERED orders delivered in the last 30 days (shown with `settled: true`) so the dashboard can show and undo recent settlements; `totalDueCents` of a group is the sum of its UNSETTLED orders and `outstandingCents` is the sum over all unsettled delivered orders.
- [finance] `/admin/expenses` and `/admin/ad-spend` lists are the standard `Page` plus `totalCents` (sum of the whole filtered range, so the dashboard totals row is right when paginated). Sort fields: `spentOn` (default, newest first), `amountCents`, `label` (category/channel), `createdAt`. `spentOn` is a date-only string stored as UTC midnight; future dates are accepted (the dashboard form restricts them).
- [insights] All figures use DELIVERED orders by `delivered_at` day in the business timezone. `series` is zero-filled from `from` to `to` (an open bound uses the first/last day with data; no data and no range gives `[]`). `bySource` always has the four sources, `byWeekday` always seven entries (0 = Sunday). `byDrop`: a pack's or Stimpie line's revenue is split equally per Stimpie unit it holds (integer cents, remainder to the first units by Stimpie id), so a drop's revenue is its Stimpies' share of sales; `orders` = distinct delivered orders containing one of its Stimpies. `products.stimpies` uses the same split. `packMix.orders` = distinct orders containing that pack (by snapshot name). `extraStimpieAttachRate` = extra-Stimpie units (STIMPIE lines) / hoodie units (PACK + HOODIE lines), exactly the business-rules formula; it can exceed 1 when customers buy many extras. `sizes`/`colors` count hoodie units from the item snapshot. Customer rates all use the selected range: `repeatRate` = customers with 2+ delivered orders in range / customers with 1+; `returnRate` = returned / (delivered + returned); `deliverySuccessRate` = delivered / (delivered + returned + cancelled-after-dispatch), where a returned order is dated by its RETURNED event (fallbacks delivered, dispatched, placed) and "cancelled after dispatch" is CANCELLED with `out_for_delivery_at` set. Zero denominators give 0. `byArea` uses the area row's name when the order has one, otherwise the typed area name, grouped case-insensitively.
- [overview] `today.newOrders` / `toPack` / `outForDelivery` are CURRENT counts of orders in NEW / CONFIRMED / OUT_FOR_DELIVERY (the cards link to those tabs); `cashToCollectCents` equals finance "cash outstanding"; `revenueCents` and `sales7d` use the finance rule (delivered, item revenue, by delivery day in the business timezone). Attention thresholds (not in the spec): `NEW_TOO_LONG` = NEW for more than 2 hours (an order whose hold has expired shows only as `HOLD_EXPIRED`), `OUT_TOO_LONG` = out for delivery more than 48 hours, at most 20 per order type, `EMAIL_FAILED` newest 10 FAILED rows. `LOW_STOCK` = an active hoodie variant (active hoodie, colour, size and per-hoodie selection) or active Stimpie (not in an ended drop) with available <= `lowStockThreshold`; an item with zero quantity is listed only if it ever held stock (a positive QUANTITY movement). Order: HOLD_EXPIRED, NEW_TOO_LONG, OUT_TOO_LONG, EMAIL_FAILED, LOW_STOCK (lowest availability first). `liveDrop`: most recently started LIVE drop; `unitsTotal` = units on hand + units sold, `unitsSold` = sold + order holds, so `total - sold` = remaining.
- [setup] Unknown setup key on `POST /admin/setup/:key/done` is 404; an AUTO key is 400 VALIDATION_ERROR (`fields.key`). `GET /admin/users` returns a plain array of the owner account(s) `[{ id, email, name, role }]`.

## WP-A: catalog, uploads, drops, content, builder

- [drops] `deriveDropState` follows business-rules 6 literally: ENDED (ended_at set or ends_at passed) wins over everything, then UPCOMING, then SOLD_OUT when no ACTIVE Stimpie has available stock (a started drop with no active Stimpies is therefore SOLD_OUT, not LIVE), else LIVE. Inactive Stimpies never count for state, `unitsRemaining` or purchasability.
- [drops] A CORE Stimpie ignores any drop in status/purchasable (never UPCOMING/ENDED); admin validation also refuses `type: CORE` together with a `dropId`, and refuses assigning a CORE Stimpie or a Stimpie that already belongs to another drop through a drop's `stimpieIds` (`stimpieIds.N`). Reason: a core Stimpie must stay always buyable and the status table says so.
- [drops] Variant `remaining` and Stimpie `remaining` are `null` at 0 units (the website never shows "0 left"; `inStock: false` / `SOLD_OUT` carries it) and `null` above `lowStockThreshold`.
- [drops] `GET /drops`: `live` is the most recently started LIVE drop; `upcoming` by `startsAt` asc; `archive` (SOLD_OUT + ENDED) by `startsAt` desc. `GET /drops` and `/drops/:slug` send `no-store` while ANY not-ended drop has `startsAt` in (now, now+60 s], else `public, max-age=10`.
- [drops] Public `Drop.stimpies` lists the drop's ACTIVE Stimpies in every state (also UPCOMING, with status UPCOMING and `purchasable: false`) because the website renders "coming soon" cards.
- [drops] `POST /drops/:id/subscribe`: e-mail is stored as typed (compared case-insensitively), WhatsApp numbers are stored normalised `+961...`; a repeat for the same drop and contact is a silent 204 (an in-process lock serialises concurrent duplicates; v1 is a single process). Any drop state accepts subscriptions (no ENDED check). Validation errors are on `fields.contact`. 10 per hour per IP (`RATE_RULES.subscribe`).
- [drops] Admin drop: `startsAt` in the past is accepted on create (the drop is then live immediately); the server does not require a future launch (the dashboard's check is UI only). `endsAt` must be after `startsAt` (`fields.endsAt`). A drop that has already started cannot be moved to a LATER start (`fields.startsAt`); moving earlier is fine.
- [drops] Relaunch: a PATCH that touches `startsAt` or `endsAt` on a drop that was ended early (`endedAt` set) clears `endedAt` when the resulting window is not over (no end, or an end in the future); a plain edit keeps it ENDED. A drop whose planned `endsAt` passed is relaunched simply by moving `endsAt` forward.
- [drops] `POST /admin/drops/:id/end` (200 + the drop): 409 CONFLICT when the drop already ended or has not started yet; a SOLD_OUT drop can be ended. Open orders are untouched.
- [drops] `DELETE /admin/drops/:id`: 409 when ANY order stock line (even a cancelled order's) references one of its Stimpies. Otherwise its Stimpies leave the drop and are hidden (`active: false`) so a deleted upcoming drop cannot suddenly make limited Stimpies buyable; its subscribers stay with `dropId = null` ("Any drop").
- [drops] Admin drop statistics: per Stimpie `remaining` = quantity - reserved, `sold` = reserved + units already delivered (order stock lines in state SOLD), `quantity` = sold + remaining. Drop totals (`unitsTotal/unitsSold/unitsRemaining`) sum ACTIVE Stimpies only (the per-Stimpie list shows every assigned one with an extra `active` flag). `revenueCents` = direct Stimpie order lines in state RESERVED or SOLD x unit price (a Stimpie inside a pack has no price of its own and adds units but no revenue). `sellOutAt` = latest availability-reducing movement (ORDER_RESERVED, CORRECTION, DAMAGED, RESTOCK, INITIAL) once every active Stimpie is at zero, else null. Extra field `endedAt` on the admin drop.
- [drops] `GET /admin/drops?state=` is derived in memory (state is not stored): UPCOMING (soonest first), LIVE, ARCHIVE (SOLD_OUT + ENDED), default order newest `startsAt` first; `sort` accepts startsAt, name, id; paged like every admin list.

- [catalog] Public lists exclude inactive rows; `GET /products/hoodies/:slug` and `/products/stimpies/:slug` return 404 for hidden ones. Hoodie `colors` on cards = active colours with at least one available variant in an active size; detail `colors`/`sizes`/`variants` = active colours/sizes that have a variant (zero-stock ones included, `inStock: false`). `GET /products/stimpies?drop=<unknown>` is an empty list (200); the `drop` filter does not bypass the includeUpcoming/includeEnded defaults.
- [catalog] Admin create and rename derive each slug from its name: lowercase letters/numbers, with spaces and punctuation converted to dashes; duplicate names get a unique suffix (`-2`, `-3`). Dashboard/API requests do not accept slug values. Renaming a drop also updates the homepage's selected-drop reference. Hoodie `costCents` defaults to 1000, Stimpie `costCents` to 600, `description`/`story` to `''`, and Stimpie `type` to LIMITED when a drop is given, else CORE. `artworkUrl` is REQUIRED when creating a Stimpie (the column is NOT NULL). `quantity` on PATCH is refused with `fields.quantity` (stock changes go through `/admin/stock`). Image/asset URLs must be http(s) (`javascript:` etc. refused).
- [catalog] Artwork width/height are copied from the matching `uploads` row (by URL) when `artworkUrl` is set or changed; a URL without an upload row gives null/null.
- [catalog] Admin hoodie `available` sums its active variants with active colours and sizes; admin Stimpie rows add `quantity`. Packs can always be deleted (orders keep name and price snapshots and reference no pack row); hoodies and Stimpies referenced by an order stock line are refused with 409 "Used by past orders. Hide it instead.". Deleting the hoodie the Builder sells is allowed; the Builder then falls back to the first active hoodie.

Limits 10 MB image, 100 MB video, 50 MB GLB (`413 FILE_TOO_LARGE`, `details.maxBytes`); unknown/corrupt content is `415 UNSUPPORTED_FILE_TYPE` (`details.allowed`). The limit is applied as soon as the first 4 KB identify the type and the rest of the stream is drained so the client gets a clean response.

SVGs are refused (415, not repaired) when they contain script, event handlers, foreignObject, entities, active content or external references (`href`/`url()`/`@import`); in-document `#id` refs and `data:image/...` base64 are allowed. `purpose` is an optional slug; `builder-model` requires a GLB. Every upload row stores `sizeBytes`; `PUT /admin/builder` reads the GLB size from it.

(must exist)}`; `policies {deliveryReturns, care, terms, privacy}` each <=20000; `about {about}` (the stored shape `{text}` is also accepted); `how-it-works {steps[{title,text,mediaUrl}], promises[], faqs[{question,answer}]}` (also accepted wrapped as `{howItWorks: {...}}`). ## WP-B: orders, stock, deliveries

- [stock] Reserve/release/sell are single conditional `UPDATE ... WHERE quantity - reserved >= :qty` statements (raw SQL only in `services/stock.ts`); rows are always touched in a fixed order (variants by id, then Stimpies by id) so concurrent carts cannot deadlock. A failed reservation rolls the whole order back: no order, no number, nothing reserved.
- [orders] `orderTxGate` (`lib/semaphore.ts`, 3 slots, in-process) wraps every order-writing transaction (`placeOrder`, `changeStatus`, hold-expiry). All of them serialise on the order-counter row lock anyway; without the gate a burst of 50 orders parked 50 transactions on 50 pool connections and the lock holder starved (Prisma P2024). With several processes each gets 3 slots; correctness still comes from the row lock, not the gate.
- [orders/counter-contention] In `placeOrder`, upsert the customer and recheck same-phone replay before taking the global order-number lock. This keeps customer work out of the serialized section; if two new-phone inserts race, the loser rolls back, rechecks replay, then retries against the winning customer. A second replay check after the counter lock preserves idempotency-key conflicts across different phone numbers.
- [orders] Order numbers come from `counters.order_number` incremented inside the order transaction (row lock), so numbers are gap-free and consecutive across rollbacks (a SOLD_OUT attempt consumes no number). A cancelled order keeps its number.
- [orders] `expectedTotalCents` is compared with the GRAND total (items + delivery fee); a mismatch is `422 PRICE_CHANGED` with `details.totalCents`.
- [orders] Idempotency: same `Idempotency-Key` + same body hash returns the original order (`200`, `created: false`); same key + different body is `409 CONFLICT` with `details.field = "Idempotency-Key"`. Without a key, an identical WEBSITE order (same phone + body hash) within 60 s of an earlier, non-cancelled one returns that order; manual orders are never de-duplicated. The check is repeated after taking the counter lock, so 10 concurrent identical requests create one order. Header format: 8 to 80 characters of `A-Za-z0-9._:-`.
- [orders] A website order is always `NEW` (even if `initialStatus: CONFIRMED` reaches the service). Only dashboard-created orders may start `CONFIRMED`; they queue `order_confirmed` instead of `order_received` and write NEW and CONFIRMED events.
- [orders] The honeypot (`hp` filled) returns `400 VALIDATION_ERROR` with `fields: {}` and a generic message; nothing is stored. The per-IP order limit (5 per 10 min) runs in `preHandler`, after body validation, so malformed requests do not burn the budget; the per-phone limit (3 per hour) uses the normalised phone.
- [orders] Customers are matched by normalised phone; the latest name / e-mail / WhatsApp win on the customer row, while each order keeps its own snapshot. A manual order without an e-mail does not erase the customer's known e-mail. Editing an order's contact (`PATCH /admin/orders/:id/contact`) changes the order snapshot only, is logged, and tracking then needs the corrected phone.
- [orders] The delivery fee and totals are fixed at placement; editing an order's delivery details (area, address, notes) never recomputes them and is refused once the order is DELIVERED, RETURNED or CANCELLED (409).
- [orders] `holdExpired` is derived (`status = NEW` and `holdExpiresAt < now`); the hold-expiry job only cancels when `settings.orders.autoExpireUnconfirmed` is on (reason "Expired: not confirmed", user null). An order confirmed in the meantime is skipped silently.
- [orders] Packs: a pack line needs exactly `stimpieCount` Stimpies, all different within the pack (error path `items.N.stimpieIds.M`); the same Stimpie may appear on several lines. A pack reserves one hoodie variant plus its Stimpies; an inactive variant or colour is reported as a `HOODIE_VARIANT` problem.
- [status] `changeStatus` reads the order, validates against the machine, then updates with `WHERE id = :id AND status = :from`; two simultaneous changes cannot both win (the loser gets `INVALID_TRANSITION`), so the event and the e-mail row are written once. WP-C's one-per-(order, template) guard therefore never races (tested with 6 parallel cancels).
- [status] Cash: `DELIVERED` sets `cashCollected`; `RETURNED` resets both flags; `POST /admin/orders/:id/cash` only works on DELIVERED orders, settled needs collected, un-collecting un-settles, and every change writes an event with `from = to`.
- [status] Delivery number: 1 to 60 characters after trimming. A "duplicate" is another order in OUT_FOR_DELIVERY or DELIVERED with the same number (returned and cancelled ones do not count). Correcting the number on an order already out writes the event "Delivery number changed from X to Y" and never resends the e-mail; from PACKED it is the normal status change.
- [status] Every status change takes an optional explicit `at` (used by the demo seed); order timestamps, events and stock movements all use the app clock (`lib/clock`), never the database `now()`, so fake-clock tests and demo data agree.
- [status] `bulk-status` runs each order in its own transaction and returns `{ updated, failed: [{ id, code }] }`; duplicate ids are processed once; only CONFIRMED, PACKED and DELIVERED are accepted.
- [e-mail] Order e-mails are queued through WP-C's `enqueueOrderEmail` inside the status transaction, wrapped so an e-mail problem never fails an order or a status change (logged as a warning). Founder "new order" alerts are sent for WEBSITE orders only. Low-stock alerts fire once per downward crossing of `lowStockThreshold`, from orders and from manual stock changes.
- [track] `POST /orders/track` always does the lookup and a constant-time phone comparison and answers an identical `404` for unknown number, wrong phone and unparseable number. Accepted number spellings: `STP-1001`, `stp-1001`, `STP1001`, `#1001`, `1001`. The timeline lists each reached status once; contact edits, notes and delivery-number corrections are not steps. Rate limit 20 per 10 min per IP (every call counts).
- [find] `POST /orders/find` is always `202` with the same body. The mail goes to the address stored on the most recent matching order (so a different capitalisation of the typed address reaches the canonical one), lists up to 10 orders, and has `order_id = null`.
- [search] Order, delivery and customer searches use `likeEscape`, so `%` and `_` match literally. `lib/like.ts` (WP-C's) first produced the literal text `${c}` instead of a backslash; it is fixed and also escapes the backslash itself. Digits-only queries match the order number by suffix and phones by digit substring (3+ digits); a full Lebanese number in any format matches exactly.
- [pagination] Collection pages use `page` and `pageSize` (defaults 1 and 25, maximum 100) and return `{ items, page, pageSize, total }`. The shared format covers entity lists, public catalog lists, stock lists, FAQ/review lists, upcoming/archive drops, finance by-order rows and cash groups. Stock hoodie grids page by hoodie; Stimpie status filters apply before totals. Settings, option lists and typeahead search remain bounded payloads.
- [list] `GET /admin/orders` uses the project-wide default `pageSize` 25, newest first; `sort` accepts `placedAt|totalCents|number|status` with an optional `-`; `number` sorts by id (numeric order) and `status` sorts in pipeline (enum) order, not alphabetically. `afterId` returns only rows with a larger id (polling). The detail's `events`, `notes` and `emails` are newest first.
- [export] `POST /admin/orders/export` returns `text/csv; charset=utf-8` with `Content-Disposition: attachment; filename="orders-YYYY-MM-DD.csv"` (business timezone), a UTF-8 BOM, CRLF records and at most 5000 rows. Cells starting with `=`, `+`, `-` or `@` (or tab/CR) get a leading `'`, which includes phone numbers beginning with `+`. `fetch().text()` strips the BOM; the bytes on the wire start with EF BB BF.
- [stock] Manual `RESTOCK` needs a positive delta and `DAMAGED` a negative one (`CORRECTION` may be either); `delta: 0` is rejected. The note is required and limited to 255 characters (the column size; the dashboard doc says 300). A change that would reduce stock below open order holds is `409 CONFLICT`. Stock read responses show quantity and available, without a reserved count. `GET /admin/stock/movements` filters by itemType + itemId (itemId alone is a 400), reason, orderId and whole business-timezone days.
- [deliveries] `GET /admin/deliveries?tab=OUT|DELIVERED` lists orders grouped by delivery number (number, then id). `POST /admin/deliveries/dispatch` handles each order in its own transaction and returns `{ dispatched, failed: [{ orderId, code }], warnings: [{ deliveryNumber, orderIds }] }`. Settle touches only orders with `cashCollected`, is idempotent and writes one event per changed order. There is no `GET /admin/areas/:id` (not in the contract); `GET /admin/areas` defaults to `pageSize` 100.
- [seed] `npm run db:seed:demo` places 30 orders through `placeOrder` / `changeStatus` with explicit `at` timestamps spread over hours after placement (never in the future) and refuses to run when orders exist unless `--force` is passed. It queues real e-mail rows to example.com addresses (in dev the worker delivers them to Mailpit).

- [orders/new] The manual order form reads the PUBLIC catalog endpoints (`/products/hoodies`, `/products/hoodies/:slug`, `/products/stimpies`, `/packs`, `/delivery/fees`) through a credential-less client (`getPublicApi()`): public routes answer CORS without `Access-Control-Allow-Credentials`, so a credentialed request from the dashboard origin is blocked by the browser. Public GETs are cached up to 30 s, so a sold-out item can still be offered; the server answers SOLD_OUT / NOT_PURCHASABLE and the form lists the problem lines.
- [orders/new] Items are one array with kinds pack / hoodie / stimpie (`items.N.field` is both the form field and the API error path, so server `fields` land on the right input). Customer search uses `GET /admin/customers?q=` (min 2 characters). `?customerId=` pre-fills. After creating, `ignoreOrder(id)` is called before navigating so the poller does not announce the dashboard's own order. `sendEmail` is only sent true when an email was typed.

- [orders/print] `/orders/:id/label` (print label) and `/orders/print?ids=1,2` (delivery sheet, max 100) are client-side views from `GET /admin/orders/:id`; print CSS hides the shell (`.no-print`, `print:hidden` on the sidebar).

- [stock] Note limit is 255 characters (the column size, DECISIONS WP-B) instead of the 300 in the dashboard doc. RESTOCK needs a positive and DAMAGED a negative change in the UI as well as on the server. A change above 50 units (also the difference in Set total) asks a second confirmation. After a save the cell is patched from the response and every stock-related query is invalidated.

- [deliveries] Out tab groups by delivery number client-side (default on from `md`, off on phones where cards use select mode).
