# CRM frontend plan (`frontend/admin`, `frontend/web`, `packages/*`)

Part of [README.md](README.md). Consume only the generated `packages/api-client` (regenerated by the backend work); do not hand-write API types. Follow existing patterns: React Query keys in `src/api/queryKeys.ts`, `QueryBoundary`, `DataTable`, `FilterBar`, `Pagination`, `Timeline`, shared `@stimpy/ui`. Everything must work at phone width. Nothing hard-coded that should be a setting.

Client-side permission checks are convenience only; the server is authoritative. Everything stays under the `customers` area in `frontend/admin/src/app/navigation.ts`; no new role.

## Phase 1: Customer profile

- Customer detail page (`/customers/:id`): header (name, phone, WhatsApp link, email, area), stat tiles (orders, lifetime value, average order, first/last order, favourite Stimpie and colour), recent orders, activity timeline using the existing `Timeline` component with infinite or "load more" pagination.
- Link from the customers list rows to this page.
- Empty states: customer with no orders, empty timeline. Loading and error states via `QueryBoundary`.

## Phase 2: Tags, notes, follow-ups

- Tag chips on the profile and list, add/remove tag via `Combobox` (create on the fly), tag filter in the customers `FilterBar`.
- Notes panel on the profile (add, list with author and time). Show legacy `Customer.notes` as a pinned "Legacy note".
- Follow-up panel on the profile (set due date and note, mark done, reopen, delete).
- New "Follow-ups" view (today / overdue / upcoming) with a count badge in navigation.
- New timeline item types (note, follow-up) render with distinct icons.

## Phase 3: Subscribers, consent, duplicates

- Profile shows consent per channel (email, WhatsApp) with timestamps, an unsubscribed marker, and linked drop signups.
- Customers list filters: "subscribed, never bought" and "bought, not subscribed".
- Duplicates screen listing candidate groups with a side-by-side compare and a merge action behind `ConfirmDialog` stating exactly what will move. Show the audit entry on the survivor's timeline afterwards.
- Public unsubscribe page in `frontend/web` for the email link (simple confirmation, no login).

## Phase 4: Segments and bulk messaging

- Segment builder built on `FilterBar`: add/remove filter rows for each backend filter, live recipient count, save as a named segment, saved segments list.
- Campaign composer: choose segment, channel, template; preview step showing recipient count, **skipped count with reason (no consent)**, and a sample; explicit confirm button. The UI must not offer any way around consent.
- Email campaign: progress and per-recipient status on the campaign history page.
- WhatsApp campaign: work-through list with a "Open chat" (`wa.me`) button per recipient and a "Mark sent" toggle; progress indicator.
- Campaign history list and detail with per-recipient status and errors.

## Phase 5: Attribution

- Storefront (`frontend/web`): on first visit capture `utm_source`, `utm_medium`, `utm_campaign` and referrer into first-party session storage, and send them with checkout. No third-party trackers; respect the storefront's existing consent behaviour.
- Admin profile: show first-touch source/campaign and first-touch date.
- Insights: customers and revenue by source/campaign, cost per customer and ROAS from the backend endpoints. Show "unknown" as its own row; use the existing chart components and theme.

## Privacy in the UI

- Add "Export data" and "Anonymise customer" actions on the profile; anonymise needs a `ConfirmDialog` with a clear irreversible warning.
- Do not put phone numbers or emails in URLs, page titles or client-side logs.

## Verification

- Exercise every new screen in real Chrome at desktop and phone width, including empty, loading, error and permission-denied states.
- Run `npm run admin:build` and `npm run web:build`, and extend `e2e` for the main flows (open profile, add tag/note/follow-up, build a segment and preview a campaign).
